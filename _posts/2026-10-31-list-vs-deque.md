学 `collections.deque` 的时候，教程都这么说：

> `list.pop(0)` 是 O(n)，`deque.popleft()` 是 O(1)，所以处理队列用 deque。

我记住了，而且从此把 deque 当成 list 的"更快版本"。

直到我改自己的日志分析工具，需要在一个时间窗口里统计**不同路径的数量**，写了这么一行：

```python
distinct = len({e.path for e in items[left : right + 1]})
```

然后发现我用的是 deque，**它不支持切片。**

那一刻我才意识到：我把"某个操作更快"记成了"整体更好"。

## 一、我原来怎么写

检测目录扫描，需要判断"某个 IP 在 60 秒内是不是产生了大量 404"。最早的版本这样写：

```python
q = deque()
for entry in entries:
    q.append(entry.time)
    while q and (entry.time - q[0]).seconds > 60:
        q.popleft()
    if len(q) >= 5:
        报告("疑似扫描")
```

很顺，很符合教程的写法。

但这段代码藏着两个问题：

**问题一：它假设数据按时间有序。**
`q[0]` 必须是"最早的那条"，`popleft()` 才能正确丢弃过期数据。一旦日志乱序（多进程写日志、后台分页导出都会乱），这个假设就崩了，窗口里装的是错的记录。

**问题二：它只能数个数，看不了内容。**
我的判定条件后来变成"404 次数 ≥ N **并且** 不同路径 ≥ M"。要数不同路径，就得遍历窗口内的所有元素。而 deque 的两个短板正好卡在这里：

| 操作 | list | deque |
| --- | --- | --- |
| `append` 尾部追加 | O(1) | O(1) |
| `pop(0)` / `popleft()` 头部移除 | **O(n)** | O(1) |
| `items[i]` 按下标访问 | **O(1)** | **O(n)** |
| `items[a:b]` 切片 | ✅ O(k) | ❌ 不支持 |
| `sort()` 原地排序 | ✅ | ❌ 不支持 |

**deque 的强项是两端增删，弱项恰恰是随机访问。**

## 二、本质只有一句话

数据结构的一切优劣，都来自它在内存里怎么摆。

| | list | deque |
| --- | --- | --- |
| 内存形态 | 一整块**连续数组** | **分块的双向链表** |
| 类比 | 一排连着的储物柜，编号 0、1、2… | 一列火车，每节车厢装若干个元素，车头车尾都能上下人 |

从"连续"出发，结论全是推出来的，不用背：

- 连续 → 知道编号就能直接跳 → **按下标访问 O(1)**
- 连续 → 往头部插一个，后面全部要往后挪一格 → **`pop(0)` 是 O(n)**
- 分块 + 首尾指针 → 车头车尾加一节是 O(1) → **`append`/`popleft` O(1)**
- 分块 → 想找第 100 个元素得从头数 → **按下标访问 O(n)**
- 分块 → 没有"连续一段"这个概念 → **不支持切片，也没法原地排序**

最后那条你甚至可以自己推：快排要频繁交换任意两个位置，分块链表定位任意位置是 O(n)，所以做不了。

## 三、所以什么时候用哪个

判断只需要问三个问题：

1. **我的数据是"先全部拿到"还是"源源不断流进来"？**
   流进来 → deque（没法预排序，需要边来边丢）
2. **我最频繁的操作是什么？**
   两端进出 → deque；按下标取、切片、排序、整体遍历 → list
3. **窗口里我只需要计数，还是要看内容？**
   只看个数 → deque 够；要统计/去重/取样 → list

对照我自己的两个场景：

| 场景 | 需要什么 | 该用 |
| --- | --- | --- |
| 离线分析一个日志文件 | 先排序、要统计窗口内不同路径 | **list + 双指针** |
| 实时 `tail -f` 盯日志 | 数据流式到达、只数个数、老的马上丢 | **deque** |

所以我后来把离线分析改成了：

```python
items.sort(key=lambda e: e.ts)   # 先排序，只做一次 O(n log n)

left = 0
for right, cur in enumerate(items):          # 双指针在有序列表上滑，整体 O(n)
    while (cur.ts - items[left].ts).total_seconds() > window:
        left += 1
    window_items = items[left : right + 1]   # 能切片，能统计
    distinct = len({e.path for e in window_items})
```

不移动数据，只移动两个下标，复杂度同样是 O(n)，但**能切片、能处理乱序**。

## 四、我改掉的三个错误认知

**错误一：「deque 比 list 快」。**
准确说法是：**deque 在两端增删上更快**。它在随机访问上比 list 慢一个数量级。

**错误二：「复杂度低的数据结构更好」。**
复杂度是**按操作**算的。选结构之前要问"我最常做的是哪个操作"，而不是"哪个结构整体更优"。

**错误三：「教程说的最佳实践可以直接套」。**
教程说"队列用 deque"，前提是你的场景真的是队列——**只从头部消费，从不看中间**。我的场景要从中间统计，那就不是队列了。

## 五、面试被问到怎么答

不要说"deque 比 list 快"，那句话经不起追问。可以说：

> 取决于操作。list 是连续数组，按下标访问和切片是 O(1) 和 O(k)，但头部插入删除是 O(n)；
> deque 是分块链表，两端增删 O(1)，但定位任意位置是 O(n)，也不支持切片和排序。
> 我项目里两种都用过：早期滑窗只数个数、假设数据有序，用 deque；
> 后来要统计窗口内的不同路径数、还要处理乱序日志，就换成了排序加双指针。

这段话的重点不是结论，是**"我根据自己的场景换过一次"**。
