给自己的日志分析工具加一条规则，本来以为是最简单的活：

> 抄一条现成的 `Rule`，换个正则，完事。

结果我踩了两个坑，**共同点是：程序从头到尾没报过一个错。**

## 起因

Spring Boot 的 Actuator 端点如果对公网暴露，`/actuator/env` 能读出环境变量
（里面常写着数据库密码），`/actuator/heapdump` 能下载完整内存转储。

这是真实存在的高危配置失误，值得加一条规则。

## 坑一：我改的不是那个文件

我的项目前后有两个目录：

```
E:\python files\sec_log_analyzer\rules.py       ← 旧目录，早期开发留下的
E:\sec-log-analyzer\sec_log_analyzer\rules.py   ← 当前项目，GitHub 上推的是这个
```

我把规则加进了**旧目录**那份。

然后兴冲冲去验证：

```
$ python tools/score.py "/actuator/heapdump"
载荷    /actuator/heapdump
命中    无 → 不告警
```

**"不告警"这个结果是正确的** —— 因为我改的那份文件，压根没被这次运行加载。

这件事的教训不是"要细心"，而是：**同一个项目存在两份副本，迟早会咬人。**
所以我后来把旧目录归档了，只保留一个可以改的地方。

## 坑二：`headdump` 和 `heapdump`

改到正确的文件之后，还是没生效。我写的是：

```python
re.compile(r"/actuator/(?:env|headdump|jolokia)")
#                        ↑ 多了个 d
```

正确的词是 `heapdump`（heap + dump，堆转储）。我打成了 `headdump`。

于是这条规则成了死代码：**语法合法、加载成功、永远匹配不到。**

## 为什么这类坑特别危险

如果正则写错成 `r"/actuator/((("`，Python 会直接抛
`re.error: missing ), unterminated subpattern`，程序启动就崩 —— 你会立刻知道。

但 `headdump` 是**合法正则**，它只是永远匹配不到东西。

在安全检测里，这种失败最坏：

> 你以为自己有这条防护，实际上没有。而且没有任何告警提示你"规则失效了"。

真实产品里这叫"规则静默失效"，是安全设备最怕的故障类型之一 ——
设备指示灯全绿，检出率已经掉到零。

## 我后来的做法：一条规则配两条用例

现在加任何规则，我都同时写两条测试：

| 用例 | 输入 | 期望 |
| --- | --- | --- |
| **该命中** | `/actuator/heapdump` | 告警，10 分 |
| **不该命中** | `/actuator/health` | 不告警 |

第二条比第一条更重要。

`/actuator/health` 是健康检查端点，生产环境每天被调用成千上万次。
如果它也被判成攻击，那这条规则上线第一天就会制造大量误报。

**只测"能抓到"，你只能证明规则活着；再测"不误抓"，才能证明规则可用。**

## 顺手把验证做成了可脚本化的

`score.py` 除了打印结果，还返回退出码：告警返回 0，不告警返回 1。

于是可以这样用：

```bash
python tools/score.py "/actuator/heapdump" && echo "这条会被拦"
```

在 shell 里，`&&` 表示"前面成功才继续"。第一次跑的时候我发现后面的 echo 没执行，
愣了一下才想起来：**是因为"不告警"返回了 1，`&&` 链断了。**

那一刻反而挺高兴 —— 说明这个退出码设计是真的能用，不是摆设。

## 加规则的正确姿势（我现在的流程）

1. 找一条同类规则，抄结构
2. 改：规则名、类别、权重、正则、说明
3. **先跑"该命中"的用例**，确认规则活着
4. **再跑"不该命中"的用例**，确认不误伤
5. 跑一遍全量回归，确认老规则没被弄坏
6. 同步文档里的规则数量

第 3、4 步是核心。**不做这两步，等于没写。**
