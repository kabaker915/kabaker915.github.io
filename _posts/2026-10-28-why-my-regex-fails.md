上一篇文章聊完蓝队的四个格子（TP / FP / FN / TN），我决定拿自己的脚本开刀。

结论先说：**7 条真实攻击，只抓到 1 条；5 条正常请求，误报了 1 条。**

## 一、第一版长这样

核心就两个正则：

```python
sqli = re.compile(r"(union\s+select|or\s+['\"]?1['\"]?=1|--|')", re.IGNORECASE)
xss  = re.compile(r"(<script>|alert\(|onerror=)", re.IGNORECASE)

for line in log:
    if sqli.search(line):
        report("发现 SQL 注入")
    elif xss.search(line):
        report("发现 XSS")
```

写的时候觉得挺合理：联合查询、`or 1=1`、注释符、单引号——教科书上的特征都覆盖了。

问题在于，**"覆盖了特征"和"能做出正确判断"是两件事。**

## 二、我怎么自测的

没有标注数据集，就用最土的办法：手写 12 条日志，其中 5 条是正常业务、7 条是真实攻击。

判正例的标准是"这条请求是不是攻击"，判负例是"这条是不是正常业务"。
然后统计系统在每条上的输出，套进四个格子里算精确率和召回率。

| 样本 | 实际 | 旧版判定 |
| --- | --- | --- |
| 姓名带撇号（编码） `/user/profile?name=O%27Brien` | 正常 | 放过 |
| 路径含双连字符 `/api/v2/item--detail` | 正常 | **告警** |
| 字体文件 `/fonts/fa-solid-900.woff2` | 正常 | 放过 |
| 搜索词含 select `/search?q=select+the+best+product` | 正常 | 放过 |
| 普通文章页 | 正常 | 放过 |
| URL 编码注入 `/p?id=1%27%20OR%20%271%27%3D%271` | 攻击 | **放过** |
| 大小写混淆 `/p?id=1+UnIoN+SeLeCt+1,2,3` | 攻击 | **放过** |
| 时间盲注 `/p?id=1%20AND%20SLEEP(5)` | 攻击 | **放过** |
| 路径穿越 `/../../etc/passwd` | 攻击 | **放过** |
| 命令注入 `/ping?host=127.0.0.1;cat+/etc/passwd` | 攻击 | **放过** |
| 编码 XSS `/s?q=%3Cimg%20onerror%3Dalert(1)%3E` | 攻击 | 告警 |
| 敏感文件 `/.env` | 攻击 | **放过** |

```
旧版：TP=1  FP=1  FN=6  TN=4
精确率 = 1/(1+1) = 50%
召回率 = 1/(1+6) = 14%
```

一次误报、六次漏报。这个结果比我预想的差很多。

## 三、根因一：`--` 和 `'` 是误报炸弹

正则里有这么一个分支：`--|'`

意思是"请求里出现双连字符或单引号就算 SQL 注入"。

但 `/api/v2/item--detail` 是一条完全正常的 API 路径。双连字符在 URL slug 里非常常见
（英文排版里叫 em dash）。这一条立刻被误判。

单引号更隐蔽。**在 nginx 的 access.log 里，撇号会以 `%27` 出现**，
所以 `O'Brien` 不会触发——但注意，这条正则扫的是**整行**，
包括 Referer 和 User-Agent。只要任何一个位置出现字面单引号，就会误报。

而且更要命的不是误报多少，而是**这个特征根本不足以支撑判断**。
一个引号在几百种正常场景里都会出现，它没有区分度。

## 四、根因二：没有做 URL 解码

`/p?id=1%27%20OR%20%271%27%3D%271`

肉眼一看就是 `1' OR '1'='1`，但正则匹配的是原始字符串，
`%27` 和 `'` 是两个完全不同的东西，所以匹配不到。

**攻击者在 URL 里不可能直接放引号和空格**，一定是编码过的。
不做解码，等于给所有攻击加了一层免费免杀。

更进一步：还有二次编码，`%2527` 解码一次得到 `%27`，解码两次才是 `'`。
所以解码要做两轮。

## 五、根因三：`\s+` 匹配不到 `+`

`union\s+select` 看起来很对。但 URL 里空格会被编码成 `+` 或 `%20`。

`1+UnIoN+SeLeCt+1,2,3` 里 `union` 和 `select` 之间是一个 `+`，
`\s` 不匹配 `+`，所以整条规则失效。

这个坑特别典型：**你以为你在匹配文本，其实你在匹配编码后的文本。**

## 六、真正的问题不是正则写得烂

修完这三个，我想了想，觉得方向本身有问题。

只要规则是"命中就告警"，就必须保证**每一条规则单独看都是可靠的**。
而现实中绝大多数特征单独看都不可靠——引号不可靠、`select` 不可靠、
甚至连 `union` 单独出现都可能只是业务文本。

真正靠得住的只有少数几个：`union select`、`sleep(`、`information_schema`、
`../`、`<script`。这些叫**强特征**。

剩下的都是**弱特征**——单独出现毫无意义，但组合起来就有意义了。

所以我把布尔判断换成了加权打分：

```python
强特征 = 10 分
弱特征 = 3 分
阈值   = 6 分
```

规则：

- 强特征单独命中 → 10 分 ≥ 6 → **立刻告警**
- 两个弱特征同时命中 → 3 + 3 = 6 → **告警**
- 单个弱特征 → 3 < 6 → **永远不告警**

这样一来，`O'Brien` 只有引号（3 分）不过线；
而 `1' OR '1'='1` 是引号（3）+ 恒真条件（10）= 13 分，且含强特征，直接命中。

**本质上是让弱特征互相背书，单个弱特征不再拥有定罪权。**

## 七、还有一个坑：真实 payload 的引号是不闭合的

改完之后我又踩了一次。恒真条件的正则我一开始写成要求引号成对：

```
'[^']*'
```

结果 `1' OR '1'='1` 还是匹配不到。

盯着看了半天才反应过来：这个 payload 最后一个 `1` **后面没有引号**。
因为闭合它的那个引号来自应用自己的 SQL 语句：

```sql
SELECT * FROM users WHERE name = '1' OR '1'='1'
```

攻击者只负责打破原有的引号平衡，不需要负责收尾。

所以正则要写成 `'[^']*'?`——结尾的引号必须可选。
这个细节不自己写一遍是想不到的。

## 八、改完之后的数字

同一批 12 条样本：

```
新版：TP=7  FP=0  FN=0  TN=5
精确率 = 100%
召回率 = 100%
```

| | 精确率 | 召回率 |
| --- | --- | --- |
| 旧版 | 50% | 14% |
| 新版 | 100% | 100% |

## 九、但我不打算说"我做到了 100%"

这句话必须写清楚，否则就是自欺欺人。

**12 条样本得出的 100% 没有统计意义。** 样本是我自己写的，
天然会偏向我已经想到的攻击类型——这是典型的过拟合。

真实环境的误报率一定会高得多，因为：

1. 正常业务流量里会出现我根本没想到的字符串组合
2. 攻击者会针对你的规则做绕过，而我的规则是公开的
3. 我只覆盖了 8 类攻击，还有 SSRF 变形、反序列化、Log4j 各种变体

所以这个 100% 只能说明一件事：**改动方向是对的**，
证明"加权打分优于单特征布尔判断"，而不是"我的检测器已经可用了"。

想要真实数字，得有一份标注过的人工数据集，几百上千条，还要包含误报样本。
这是我下一步想做的事。

## 十、顺带修掉的三个 bug

改的过程中还发现几个跟检测无关、但更基础的问题：

**1. 报告里的时间是 1900 年**

`report.txt` 里写着 `初始时间:1900-01-15 03:22:01`。

原因：syslog 的时间格式是 `Jan 15 03:22:01`，**没有年份**。
`datetime.strptime` 遇到没有年份的格式，默认填 1900。

正确做法是先假设是今年，如果补出来的时间比现在晚超过一天，
说明这是去年 12 月的日志（跨年），年份要减一。

**2. `.seconds` 用错了**

```python
while (t - q[0]).seconds > window:   # 错
```

`timedelta.seconds` 只取"秒位"，超过一天会把天数扔掉。
更麻烦的是**差值为负时**，`.seconds` 会返回一个巨大的正数——
日志只要不是严格时间升序，窗口判断就彻底失效。

应该用 `total_seconds()`。而且**必须先按时间排序**，
日志不保证有序（多进程写、翻页导出都会乱）。

**3. `line.split()[0]` 没有保护**

遇到空行、前导空格、畸形行，直接 `IndexError`，整个分析中断。

一条坏数据不该让整批数据报废。这是日志处理的第一原则。

## 十一、如果面试问到这个项目

我现在会这么讲：

> 我第一版用的纯正则，自测精确率 50%、召回率 14%。
> 定位到三个根因：弱特征被当成强特征、没有 URL 解码、`\s+` 匹配不到编码后的空格。
> 改成加权打分后，同批样本精确率和召回率都到了 100%，
> 但我很清楚这是小样本过拟合，只能说明方向对，不能说明系统可用。
>
> 另外我特意保留了这个对比数据，因为**能讲清自己错在哪，比讲功能更有说服力**。
